# PRD 原型标准

仅在用户明确要求原型时读取并应用。原型是 PRD 的可视化验证层，不是默认交付物。

## 1. 交付形态

默认生成单文件 HTML：

- 内联 CSS 和 JavaScript；
- 不依赖 CDN、构建工具或网络资源；
- 双击即可打开；
- 桌面端优先，同时提供基本响应式布局；
- 若同文件包含 PRD，顶部提供“原型 / 完整 PRD”清晰切换；
- 视图切换、弹窗、筛选、标签页或展开收起必须真正可操作。

用户只要求静态线框图时，不必过度实现交互。用户指定 Vue、React、Figma 或其他载体时服从指定技术形态。

## 2. 视觉策略

第一优先级是匹配用户提供的现有产品截图或设计系统。复用其导航位置、内容宽度、圆角、字体层级、品牌色、卡片密度和控件风格。

没有现有视觉依据时，使用克制、专业的蓝白后台风格：

- 主文字 `#14283c`；
- 次文字 `#6f8497`；
- 边框 `#d9e5ee`；
- 页面背景 `#f7fafc`；
- 面板 `#ffffff`；
- 主色 `#1684ff`；
- 深蓝 `#0e5eb8`；
- 浅蓝 `#e9f4ff`；
- 成功 `#159570`；警告 `#e69627`；错误 `#d85b5b`；
- 中文字体优先使用 `Avenir Next, PingFang SC, Hiragino Sans GB, Microsoft YaHei, sans-serif`；
- 使用轻边框、有限阴影、明确留白和紧凑数据表，避免装饰性渐变堆叠。

页面常用层次：

1. 顶部品牌栏：产品名、视图切换、版本或运行状态；
2. 左侧菜单：保留现有菜单并突出本次新增入口；
3. 页面标题区：一句说明 + 主要规则/帮助按钮；
4. 筛选区：统计周期、平台、用户状态及业务筛选；
5. 核心指标卡；
6. 对比表、漏斗、趋势或业务模块；
7. 数据口径、API、质量或说明模块。

只使用实际支持需求理解的模块。不要为了视觉丰满虚构业务。

## 3. 原型数据

- 能读取真实数据时使用真实数据并注明来源时间。
- 开发阶段没有真实数据时可以使用少量结构占位，但页面必须显著标注“原型示例，不代表生产数据或估算”。
- 不把占位数值用于推导结论、阈值或运营建议。
- 如果用户明确不想看到数值，使用 `—`、空状态或字段结构，不擅自估算。
- `N=0`、低样本或窗口未成熟的表现必须遵守 PRD 规则，不能由原型另设门槛。

## 4. 必须覆盖的状态

按功能需要体现：

- 默认/已加载；
- 筛选后；
- 空状态；
- 加载中；
- 加载失败与重试；
- 部分数据；
- 无权限；
- 规则说明弹窗打开/关闭；
- 交互行、标签或菜单的选中态。

原型不必同时把所有状态铺在首屏，可通过控件、状态切换或 PRD 中的状态说明覆盖。

## 5. 规则说明入口

指标、运营、审批、计费或其他规则密集页面，应提供清晰的规则入口。规则弹窗或抽屉至少包含：

- 纳入范围与排除范围；
- 指标/状态口径；
- 时间窗口；
- 数据源和刷新频率；
- 去重、归因或优先级规则；
- 空数据、部分数据和异常处理；
- 规则版本和更新时间；
- 后续可扩展位置。

## 6. PRD 与原型一致性

逐项核对：

- 菜单名、页面名和角色；
- 字段名、筛选项和默认值；
- 状态、按钮和可执行动作；
- 规则、时间窗口和数据源；
- API 读写方向和权限；
- P0/P1/P2 的实际覆盖；
- 空状态与异常反馈；
- 原型示例数据免责声明。

原型中出现而 PRD 未定义的功能，要么补入 PRD，要么从原型删除。

## 7. 验证

交付前至少完成：

1. HTML 文件存在且可直接打开；
2. 抽取内联脚本并使用 `node --check` 或等效方式检查语法；
3. 点击主要导航、弹窗、筛选和视图切换；
4. 预览首屏，检查文字溢出、层叠遮挡、横向滚动和小屏布局；
5. 搜索 PRD 中的关键规则，确认原型文案与之完全一致；
6. 确认没有把示例数字写成生产数据、估算或启动阈值。
