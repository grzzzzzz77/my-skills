# PRD 质量标准

创建或修改 PRD 时完整应用本文件。按需求裁剪章节，但不得省略最小任务契约、范围、交互状态和验收闭环。

## 1. 最小任务契约

### 目标

写清本次要改变的业务结果、用户行为或系统能力。每条目标均应可在本期交付后验证。

### 非目标

列出容易被误解为本期范围、但明确不做的能力。包括未来项、外部系统职责和不承诺的效果。

### 输入

分别列出产品输入与工程输入：已确认规则、平台、角色、现有系统、接口、数据源、截图、代码和依赖。

### 交付物

列出实际要交付的页面、接口、数据模型、任务、文档和配置。原型只在用户明确要求时出现。

### 验收

使用“给定—当—则”或可核对清单，覆盖主流程、边界、权限、数据一致性和异常恢复。

### 停止条件

说明什么情况下可结束本期、什么情况下必须停止并等待新决策，例如：

- 本期 P0-P2 全部满足验收且无阻断缺陷；
- 关键数据源、业务 owner 或权限授权不存在；
- 新需求改变目标、数据方向或安全边界，需要重新确认范围；
- 只剩已明确排除的未来能力，不继续扩张本期范围。

## 2. 推荐正文结构

按需选用以下顺序：

1. 文档信息与版本记录；
2. 最小任务契约；
3. 背景与问题；
4. 产品目标、成功标准和护栏；
5. 已确认产品决策；
6. 术语、事实源和数据边界；
7. 用户、角色、权限与核心场景；
8. 总体业务链路；
9. 功能范围与优先级；
10. 详细功能与业务规则；
11. 状态机与异常路径；
12. 数据、埋点、指标与归因口径；
13. 接口、数据实体和系统职责；
14. 信息架构与页面交互；
15. 权限、隐私和安全；
16. 灰度、兼容、迁移与回滚；
17. 验收矩阵与 Definition of Done；
18. 未决问题；
19. 版本历史。

章节编号应稳定。修改旧版时优先沿用已有编号，避免无意义重排。

## 3. 规则表达

每条复杂规则至少回答：

- 适用对象；
- 触发条件；
- 计算或处理方式；
- 唯一标识和去重规则；
- 时间窗口；
- 数据来源与权威级别；
- 展示方式；
- 异常与恢复方式。

需要表格时推荐列：`规则项 | 定义 | 数据源 | 边界 | 验收方式`。

## 4. 状态机

为真实交互状态建模，不把按钮动作误写成状态。推荐表格：

| 当前状态 | 进入条件 | 可执行动作 | 下一状态 | 用户反馈 |
|---|---|---|---|---|

至少考虑：初始、加载、成功、空、失败、部分成功、无权限、过期/陈旧。仅保留适用于本功能的状态。

## 5. 异常路径

推荐表格：

| 异常 | 触发条件 | 系统行为 | 用户可见反馈 | 恢复/补偿 |
|---|---|---|---|---|

覆盖网络失败、重复请求、并发、超时、权限变化、数据源缺失、部分结果、旧版本兼容和幂等问题中适用的部分。

## 6. 数据与指标

指标必须写清：

- 名称和业务含义；
- 分子、分母；
- 统计对象与去重键；
- 时间窗口和时区；
- 数据源；
- 刷新频率；
- 缺失值、零值和部分数据的展示；
- 是否是事实、关联、推断或实验因果结论。

不自动设置最低样本数。用户选择从第一条数据开始时，写明 `N=0` 为空状态、`N≥1` 即展示；时间窗口成熟度不得被误用为采集或展示门槛。

## 7. 优先级与版本边界

- `P0`：主链路不可缺少，缺失则产品不可用或不可验收。
- `P1`：本期承诺的重要完整性能力，缺失会显著降低业务可用性。
- `P2`：本期承诺的增强能力，必须仍有明确验收；不是模糊的“有空再做”。
- `Later`：记录但不进入本期交付和验收。

用户指定本版实现 P0-P2 时，验收和 DoD 必须覆盖三档，而不是只实现 P0。

## 8. 验收矩阵

推荐列：

| ID | 优先级 | 场景 | 前置条件 | 操作 | 预期结果 | 异常验证 |
|---|---|---|---|---|---|---|

验收必须能映射回目标、功能、数据规则或接口。避免只验收“页面存在”。

## 9. 事实纪律

- 现状事实：有文件、代码、接口或用户确认支撑。
- 产品决策：用户明确接受或指定。
- 建议方案：明确使用“建议”，不得伪装成现有能力。
- 假设：集中列出并允许后续替换。
- 未决问题：说明影响面和需要谁决策。
- 示例数据：显著标注“原型示例/占位”，不得称为估算或生产数据。

任何方向性修正都要全局传播。例如数据消费者与数据源方向发生修正时，同步检查架构图、接口、异常路径、权限、验收和原型文案。

## 10. 测试标准与操作边界

PRD 必须定义“测试什么、谁来执行、允许使用什么工具、什么证据算通过”，不得只罗列验收场景。

### 10.1 默认责任边界

| 测试层 | 默认执行人 | Agent 默认可执行 | 默认不可执行 | 通过证据 |
|---|---|---|---|---|
| Agent 服务 | Agent | 单元、集成、契约、API、任务、权限、幂等、数据与日志测试 | 生产写入、真实触达、真实支付 | 测试输出、响应、数据库断言、任务日志 |
| 数据与规则 | Agent | 合成事件、窗口、去重、聚合、回补、空值和异常夹具 | 用生产用户数据制造测试样本 | 输入夹具、期望值与实际值对照 |
| H5 页面 | 用户 | Agent 可静态审查代码和生成手动步骤 | 默认不启动或操控浏览器，不自动点击、登录、支付 | 用户截图、录屏、操作记录或明确确认 |
| 小程序 | 用户 | Agent 可提供测试清单和预期结果 | 默认不操控小程序、开发者工具、模拟器或真机 | 用户截图、录屏、控制台记录或明确确认 |
| 原型 HTML | Agent + 用户 | Agent 做文件、结构、脚本语法和规则一致性检查 | 默认不操控浏览器验证交互 | 静态校验结果；交互部分由用户确认 |
| 第三方平台/支付 | 用户或获授权测试人员 | Agent 仅验证 mock、sandbox 回调和服务端幂等 | 真实支付、真实充值、真实投递、真实消息触达 | 沙箱回执或授权人员的人工结果 |

如果用户在当前任务中明确授权浏览器或小程序自动化，可以扩大范围，但必须先确定测试环境、测试账号、允许动作、禁止动作和数据清理方式。一次授权不自动延续到后续任务。

### 10.2 测试结果状态

- `通过`：Agent 已执行且有可复核证据；
- `人工通过`：用户或指定测试人员已操作并回传证据或明确确认；
- `待人工验证`：需要 H5/小程序操作但尚未收到结果；
- `失败`：实际结果不符合预期，并记录复现条件；
- `阻塞`：缺环境、账号、权限、测试构建或依赖；
- `未执行`：不在当前测试轮次或尚未开始。

不得将代码已实现、静态检查通过、原型可打开或 Agent 接口测试通过，等同于 H5/小程序人工交互已经通过。

### 10.3 测试数据边界

- 默认使用测试环境、测试账号和合成数据；
- 不使用真实用户隐私数据构造测试样本；
- 不执行真实支付、真实 Token 扣减、真实投递、真实触达或不可恢复的生产修改；
- 幂等、退款、冲正、迟到回补等场景使用 fixture、mock、sandbox 或可回滚测试数据；
- 测试数据必须带可识别标记并支持清理，不得混入生产运营统计；
- 未获得明确授权时，不安装或启动浏览器控制、小程序控制、模拟器自动化工具。

### 10.4 进入与退出标准

Agent 侧测试进入条件：测试环境可用、依赖接口可 mock 或 sandbox、迁移完成、测试账号/密钥具备最小权限。

人工 UI 测试进入条件：可测试构建已发布、测试账号可用、操作清单和预期结果已提供。

测试轮次退出条件：

- Agent 负责的 P0-P2 用例均有明确结果；
- H5/小程序用例均为“人工通过”、明确失败或带原因的“待人工验证/阻塞”；
- 失败项有复现步骤和影响范围；
- 不把待人工验证项写成已验收；
- 最终报告分别汇总自动测试与人工测试，不使用模糊的“全部测试通过”。
