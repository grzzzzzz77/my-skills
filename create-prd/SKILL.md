# Create PRD

把零散讨论和现有材料整理成产品、设计、研发和测试可共同执行的需求契约。保持事实、产品决策、合理假设和待确认项相互分离。

## 先选择输出分支

在开始写作前明确 `delivery_mode`：

1. `prd_only`：默认模式。只产出 PRD，不生成原型、线框图、页面稿或原型代码。
2. `prd_with_prototype`：仅当用户明确说出“原型”“交互稿”“页面稿”“wireframe”“后台看板原型”“可交互 HTML”或同等明确指令时启用。
3. `discussion`：用户要求先讨论几轮时，先澄清和记录决策，不提前生成最终 PRD；收到“可以生成”“写成 PRD”等指令后再切换到前两种模式。

不得因为需求涉及页面、看板、交互，或因为原型“可能更直观”而自行进入 `prd_with_prototype`。

把交付格式与是否包含原型分开判断：

- 用户只要求 Markdown：按当前 `delivery_mode` 交付 Markdown。
- 用户只要求 HTML：可以把 PRD 渲染成 HTML，但不得因此增加原型。
- 用户明确要求“PRD + 原型”：生成两者；默认可整合为一个带视图切换的独立 HTML。
- 用户指定文件名、目录、拆分方式或替换旧文件时，服从用户的文件约束。

## 执行流程

### 1. 读取真实上下文

读取用户提供的讨论记录、产品文档、截图、代码、接口说明和已有页面。优先复用现有术语、菜单、角色、状态、数据源和视觉语言。

只在会实质改变范围、数据方向、角色权限、交付形态或验收标准时追问。把相关问题合并成一轮，避免逐个打断。能够从材料确定的内容不要重复询问。

### 2. 建立决策账本

在写正文前内部整理：

- `confirmed`：用户或现有系统已经确认的事实与决策；
- `assumed`：为使文档闭合而采用的可逆假设；
- `open`：缺少答案且会影响实现的事项；
- `excluded`：明确不在本期范围的内容。

不得把未来能力写成当前依赖，不得把消费者写成数据源，不得把示例数据写成真实数据或估算结论。

### 3. 写最小任务契约

每份 PRD 开头必须包含：

- 目标；
- 非目标；
- 输入；
- 交付物；
- 验收；
- 停止条件。

用可验证语言表达，避免“体验更好”“完善体系”等无法验收的表述。详细模板和完整结构见 [references/prd-standard.md](references/prd-standard.md)。创建或修改 PRD 时必须完整读取该文件。

### 4. 补齐实现闭环

根据需求选择必要章节，不为凑模板添加空洞内容。至少覆盖：

- 背景与问题；
- 用户、角色和核心场景；
- 范围、优先级和明确非目标；
- 业务规则、名词口径和数据方向；
- 主流程；
- 数据、接口、权限、隐私或埋点要求；
- 验收标准、灰度/兼容/回滚和 Definition of Done；
- 未决问题与版本记录。

涉及交互功能时，必须追加：

- 状态机：状态、进入条件、允许动作、退出条件；
- 异常路径：触发条件、系统行为、用户可见反馈、恢复方式；
- 空状态、加载态、成功态、失败态、部分成功态和无权限态中实际适用的状态。

涉及数据量化时，不得擅自创造样本门槛、成功阈值、因果结论或预测数字。是否需要阈值由业务目标和用户决策确定；样例数字必须标注为展示占位，不得冒充估算。

### 5. 生成原型（条件分支）

只有 `delivery_mode=prd_with_prototype` 时，完整读取 [references/prototype-standard.md](references/prototype-standard.md) 并执行。

原型必须服务于本次需求的关键决策和交互，不制作与范围无关的页面。原型中的菜单、字段、状态、规则、权限和文案必须与 PRD 一致。

如果用户没有明确指定原型技术形态，优先生成单文件、离线可打开、响应式的 HTML/CSS/JavaScript 原型。若同时交付完整 PRD，默认提供“原型 / 完整 PRD”视图切换；若用户要求分开文件则分开交付。

### 6. 一致性检查

交付前逐项检查：

- 目标、范围、流程、接口、数据方向和验收是否互相支持；
- 优先级是否覆盖用户指定的版本范围；
- 所有交互是否有状态机和异常路径；
- 所有指标是否有分子、分母、窗口、去重和数据源（适用时）；
- 示例、占位、推断和真实数据是否清楚区分；
- PRD 与原型的菜单、字段、状态和规则是否一致；
- 是否误生成了用户没有要求的原型；
- 文件是否保存到用户指定位置，旧文件是否按指令保留或替换。

生成 HTML 时，至少验证 HTML 可打开、内联 JavaScript 语法有效、主要交互可达；环境允许时进行视觉预览，检查溢出、遮挡和响应式布局。

## 写作规则

- 先写产品结论，再解释原因。
- 使用产品、设计、研发和测试都能理解的具体语言。
- 用表格承载规则映射、角色权限、字段、状态和验收矩阵；简单内容保持短段落。
- 关键规则必须出现于正文和验收，而不是只存在于原型文案。
- 使用 `P0/P1/P2` 时明确每一级包含什么，不默认把未来项混进本次交付。
- 不把模型推断当作权威业务事实；标注事实源、消费者和读写方向。
- 不为了“完整”虚构接口、数据表或指标。建议项要标为建议，并说明其依赖。
- 如果用户修正理解，沿文档全局修改相关流程、接口、表格、原型和验收，不只改被指出的一处。

## 交付约定

默认文件名：`{功能名}-PRD-V1.md`。

仅当用户明确要求原型且选择单文件整合时，使用：`{功能名}-PRD-V1.html`。页面内同时包含原型和完整 PRD；若用户明确要求 HTML 替换 Markdown，可只保留 HTML。

最终回复说明：交付文件、输出模式、关键边界和完成的验证。不要声称生成了未实际创建或未验证的内容。
