# 高德打车发票 / 行程单 — 样例字段提取规范

> 基于 `skill/assets/samples/` 下两对真实样例（T3出行 23.36 元、喜行约车 21.80 元）的字段提取分析。
> 本文件是 **事实陈述**，描述这两类 PDF 的结构。M2 解析器（`parse_invoices.py` / `parse_trips.py`）按此实现。
> 报销筛选规则**不**在本文件，见 [skill/assets/rules.example.json](../assets/rules.example.json)。

## 1. 发票 PDF（电子发票 普通发票）

### 1.1 必有字段

| 字段名 | PDF 中文本锚点 | T3 样例 | 喜行样例 | 说明 |
|--------|--------------|--------|--------|------|
| 标题 | "电子发票（普通发票）" / "旅客运输服务" | ✓ | ✓ | 用于识别"这是一张打车发票" |
| **发票号码** | "发票号码：" | `26337000000434021452` | `26437000000188003500` | **去重 key**，唯一 |
| 开票日期 | "开票日期：" | `2026年05月14日` | `2026年05月14日` | 中文日期格式 |
| 购买方名称 | "购买方信息 / 名称：" | `杭州找北智职智能科技有限公司` | 同 | 报销资格校验 |
| 购买方税号 | "统一社会信用代码/纳税人识别号：" | `91330105MAELDNK7XF` | 同 | 校验购买方身份 |
| 销售方名称 | "销售方信息 / 名称：" | `浙江智捷领行信息科技有限公司` | `湖南喜行网络科技有限公司` | 各服务商不同 |

| 税额 | 表格"税额"列 | `0.68` | `0.63` | |

| 开票人 | "开票人：" | `陈乐` | `段娟` | 不重要 |

### 1.2 **空白字段**（高德发票特性）

发票 PDF 中**有这些字段标题但没有内容**：

> 出行人 / 有效身份证件号 / 出行日期 / 出发地 / 到达地 / 等级 / 交通工具类型

这意味着 **起终点 / 行程人 / 行程时间这些"行程"信息无法从发票 PDF 提取**，必须依赖配对的行程单 PDF。

## 2. 行程单 PDF（高德地图打车 AMAP ITINERARY）

### 2.1 头部字段

| 字段名 | PDF 中文本锚点 | T3 样例 | 喜行样例 | 说明 |
|--------|--------------|--------|--------|------|
| 标题 | "高德地图—打车——行程单" / "AMAP ITINERARY" | ✓ | ✓ | **平台识别**：仅高德 |
| 申请时间 | "申请时间：" | `2026-05-14` | `2026-05-14` | 开票申请日期，**不是行程日期** |
| **行程时间起** | "行程时间：" 之后 "..." 之前 | `2026-05-11 22:49` | `2026-05-09 01:36` | **报销规则看这个时间** |
| 行程时间止 | "...至..." 之后 | `2026-05-11 23:07` | `2026-05-09 02:02` | |
| **行程人手机号** | "行程人手机号：" | `17804974831` | `17804974831` | 身份校验 |
| 行程总数 | "共计N单行程" | `1单` | `1单` | 用于循环 |
| **合计金额** | "合计...元" | `23.36元` | `21.80元` | **必须等于发票价税合计**（配对依据） |

### 2.2 行程表格（每单一行）

表头：`序号 | 服务商 | 车型 | 上车时间 | 城市 | 起点 | 终点 | 金额`

| 字段名 | T3 样例 | 喜行样例 | 说明 |
|--------|--------|--------|------|
| 服务商 | `T3出行` | `喜行约车` | 高德平台下的承运方，差异较大不建议作为规则维度 |
| 车型 | `经济型` | `特惠快车` | 不建议作为规则维度 |
| 上车时间 | `2026-05-11 22:49` | `2026-05-09 01:36` | 与"行程时间起"一致 |
| **城市** | `杭州市` | `杭州市` | 规则维度候选 |
| **起点** | `中国杭州人力资源服务产业园` | 同 | 规则维度候选（可能是公司位置） |
| **终点** | `浙江大学(紫金港校区)校医院` | 同 | 规则维度候选 |
| 单条金额 | `23.36元` | `21.80元` | |

### 2.3 多行程的处理

我们的两份样例都是 `共计 1 单`。但行程单 PDF 设计上支持多单（表格多行）。**M2 解析器必须按表格行循环提取**，不能假设只有一行。

## 3. 发票 ↔ 行程单 的配对依据

由可靠性高到低：

1. **价税合计金额匹配**：发票"小写" == 行程单"合计金额"。最稳。
2. **行程人手机号 + 申请时间**：行程单上的两个字段都能交叉。但发票上没手机号，所以这一项只用于"组内排序"，无法跨发票配对。
3. **文件名后缀**：邮件附件文件名通常含 `【平台-金额-N 个行程】发票.pdf` / `【...】行程单.pdf`。**不可单独依赖**（命名可能变），可作为辅助校验。

**配对算法建议（M2 实施时参考）：**
- 把所有发票按价税合计金额做 key，所有行程单也按合计金额做 key，相同金额配对
- 若同金额出现多张，再用申请时间 / 开票日期辅助
- 配对失败的单独留出，让 Agent 提示用户人工处理

## 4. 解析器实现建议（写给 M2 阶段的开发者）

- 用 `pdfplumber.open(path).pages[0].extract_text()` 拿整页文本
- 用 `re.search` + 锚点字符串（"发票号码：" / "价税合计（大写）" 等）定位字段
- 中文日期格式 `2026年05月14日` 转 ISO `2026-05-14`：`re.sub(r'(\d+)年(\d+)月(\d+)日', r'\1-\2-\3', s)` 后再用 `datetime.strptime` 校验
- 行程单表格列对齐稳定，可用 `pdfplumber.page.extract_tables()` 直接拿结构化行
- 金额比对统一转 `Decimal`，避免浮点误差（注意 `21.1650485436893` 这种长小数会出现）

## 5. 后续扩展时需要重新验证的点

如果未来扩展到非高德平台（滴滴、首汽、出租车等），以下假设可能失效：

- 发票 PDF 中"出行人/起终点"是否仍为空白
- 行程单 PDF 是否仍是"AMAP ITINERARY"标题
- 字段锚点文本是否相同（"申请时间：" / "行程时间：" 等）
- 配对依据"金额相等"是否仍成立（如果发票包含多次行程合并开具，可能不成立）
