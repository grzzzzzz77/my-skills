# 求职深度分析与职业发展规划报告

根据用户的简历和求职需求，融合三类数据源——**简历内容** + **沉淀的行业知识**（`references/`）
+ **实时市场数据**（Web Search）——生成一份**个性化、有实质参考价值的求职分析与发展规划报告**。
报告的唯一目的是把"这个人现在处境如何、问题在哪、该怎么走"讲透，给出真能照着做的建议、规划与资源；
**不含任何推销、服务导流或公司业务承接内容**。

## 角色说明（重要）

- **本 skill 直接面向求职者本人**（也可由老师 / 家长协助操作，但报告读者与交互对象都是求职者本人）。
  因此 Agent 的所有交互——信息确认、追问补充、给建议——都**直接面向用户本人**，可以亲切、具体、为你着想。
- **报告是给你自己看的深度分析与规划**，语气面向求职者，遵循 `references/report-style-guide.md`：
  专业但不居高临下、诚实有建设性、数据驱动、不制造焦虑、不做保证性承诺。
- **报告里不出现任何推销、套餐、价格、"联系某某老师 / 我们能帮你做什么"之类的导流内容**。
  报告以"资源与下一步"自然收尾——给的是你能自己上手的外部资源和行动指引，而不是把你导去任何付费服务。

## 总体流程

1. **信息采集**：从用户简历和对话中提取所需字段（见"信息采集指引 / 输入 Schema"）
2. **信息确认**：先向用户复述已提取到的关键信息，并主动追问"还有信息要补充吗？"
   **必须等到用户明确表示没有额外信息后，才能进入后续步骤**（见"信息确认关卡"）
2.5 **学历路由**：根据 `degree` 判断走「本科 +」还是「专科 / 高职」track，决定加载哪套知识库与
   报告结构模板（见"§1.6 学历路由"）。**这一步决定了后面所有模块的口径，必须先分流再加载。**
3. **知识加载**：读取 `references/` 下**对应 track** 的知识库文件
4. **实时搜索**：执行 3-5 次 Web Search 获取市场、政策与方向数据（搜索 0/4 视情况触发）
5. **报告生成**：按 `templates/report-structure.md` 的模块结构逐模块生成；8 个模块写完后，
   **回头补写报告开头的「核心结论速览 + 信息说明」**（它是正文结论的浓缩，见模板开头）
6. **输出交付**：**最终产物必须是 Word(.docx)**。先把报告写成 Markdown 中间稿，
   **过一遍"§5.1 交付前内容自检"关卡**，再调用 `scripts/build_docx.py` 转成干净排版的 .docx（见"5. 输出格式"）
7. **A/B 双版本产出**：上一步产出的是**完整报告（B 版）**。在 B 版基础上**再拆一个速览版（A 版）**——
   抽取「核心结论速览」+「简历诊断速查表」，并在末尾加一行升级说明（见 §5.2）。两版都转 .docx 交付。

> ⚠️ **不要在用户首次提交简历和需求后就直接生成报告**。必须先完成"信息确认关卡"，
> 由用户确认信息齐全后再开始。

> 核心原则贯穿全流程：**有数据用数据，没数据就降级兜底，绝不编造**。学校分档、政策数字、
> 薪资区间这类信息，搜不到 / 查不到时使用通用表述或提示用户自行核验，不得虚构。

## 1. 信息采集指引

从**用户提交的简历和需求信息**中提取以下字段。如果缺少某些字段，可以向**用户本人**
追问，但**追问一次不超过 3 个问题**，优先基于已有信息生成报告。

> 简历可能以多种形态提交（纯文本/粘贴内容、PDF、Word、截图/图片等）。无需特殊适配，
> 直接读取其中的简历信息即可。

> **隐私（PII）约束**：简历里的手机号、身份证号、家庭住址、生日等敏感信息**仅用于本次分析，不写进交付报告**。
> 报告正文需要称呼时只用**姓名**，涉及地域只到**城市/省份**粒度。详见 `references/report-style-guide.md` 全程红线。

### 输入 Schema

**必填字段（缺少则报告无法生成）**：
- `school`：毕业院校
- `major`：专业
- `degree`：学历层次（**专科/高职 · 本科 · 硕士 · 博士**）。**决定走哪条报告 track**（见 §1.6 学历路由）
- `graduation_year`：毕业年份（如 2025）
- `target_city`：目标求职城市

> **专科 / 高职学生额外必填 `current_grade`（当前年级 / 是否应届）**：专科 track 的核心模块要判断
> "统招专升本还来不来得及"，这强依赖当前年级 + 咨询时间。简历只有毕业年份时可结合当前日期推算
> （多数 3 年制：毕业当年=大三/应届），不确定则在确认关卡向用户核实。
>
> **专科 / 高职学生额外建议确认 `zsb_status`（是否已报考本年度统招专升本 / 在等录取结果）**：
> 简历通常**不会写**这条，但它直接决定模块 3 的方向——若你其实已报考、正在等结果，报告就不该按
> "以就业为主"写，而要按"准备入学本科"安排。**尤其当你正值毕业季、本省今年专升本考试已结束时
> （此时只看简历会默认你放弃了升学）**，务必在确认关卡问一句。默认未报考时，报告以就业为主线，
> 并在模块 3 留一句"若已报考在等结果请说明"的兜底。

**从简历中提取（有则用，无则标注缺失）**：
- `gpa`：GPA 或排名
- `tech_stack`：技术栈/技能列表
- `projects`：项目经历（名称、简述、技术栈、个人角色、成果）
- `internships`：实习经历（公司、岗位、时长、工作内容）
- `competitions`：竞赛/证书/论文
- `student_work`：社团/学生干部经历

**用户补充（如未从简历获取则询问，受 3 问上限约束）**：
- `target_direction`：期望岗位方向（如：后端开发/前端/算法/测试/不确定）
- `salary_expectation`：期望薪资范围
- `job_status`：当前求职状态（未开始/已投递无回音/面试中/已拿 offer 在比较）
- `job_stage`：**身份 / 求职阶段**（在校应届找校招 · 在校找实习 · 已毕业 gap 找实习/工作 · 转专业/跨方向求职 ·
  考研保研并行 · 考公考编并行 · 二战 等）。**这决定整条求职路径**（应届政策窗口、可投递路径、时间窗口、实习 vs 正式口径都随它变），
  是模块 3「求职路径研判」的关键输入。多数可从简历 + `graduation_year` + 对话推断；推断不出且影响判断时，在确认关卡问一句。
- `concerns`：最担心的问题或最想了解的方面
- `target_employer_type`：目标雇主类型（**国央企/体制内 · 互联网大厂&成长型民企 · 外企 · 中小私企 · 不确定/多手准备**）。
  **影响简历侧重、笔面试准备、投递节奏与渠道**——四类策略差异很大（见 `references/employer-type-strategy.md`）。
  缺失或选"多手准备"时，报告就这位用户**最可能投的 2-3 类做对比**，不强制其选一类。
- `hometown`：户籍 / 生源地（省市即可）。**影响政策福利的适用性**——落户补贴、人才引进等
  常区分本地 / 外地生源。缺失时政策模块（本科模块 6 / 专科模块 6）只做通用提醒、不替你判定能否申领（见搜索 2）

## 1.5 信息确认关卡（生成前必经）

完成信息采集后，**不要立即进入知识加载和报告生成**。先向**用户本人**做一次信息确认：

1. **复述已掌握的信息**：用简洁的列表向用户回显从简历和需求中提取到的关键字段
   （必填字段 + 已获取的选填/补充字段），让用户一眼核对"系统理解到的情况"是否准确。
2. **指出缺失或不确定的项**：如有必填字段缺失或某些信息模糊，在此一并提示用户。
   - 若 `hometown`（户籍/生源地）缺失，提示用户："如能补充户籍/生源地，政策福利部分能判断得更准
     （落户、人才引进等常区分本地/外地生源）；不补也可生成，但政策只能做通用提醒。"
   - 若 `target_employer_type`（目标雇主类型）未知，可顺带一问："你更想冲哪类单位——国央企/体制内、
     互联网大厂或成长型民企、外企、还是中小私企？不同类型的简历侧重和准备重点不一样。不确定也行，
     报告会按你最可能投的几类做对比。"**不阻塞生成**。
   - **（仅专科 / 高职 track）**确认 `zsb_status`：提示用户"想跟你确认一下——
     **你是否已经报考本年度统招专升本、或正在等录取结果？** 这决定报告是按'以就业为主'还是'准备入学本科'来写。
     **如果你正值毕业季、本省今年考试已结束**，仅凭简历会默认你放弃升学，所以这一句尤其要问。"
3. **主动追问**：明确询问用户 **"还有信息要补充吗？"**（例如更多项目细节、实习经历、
   特别关注的方向或城市、特殊情况等）。
4. **等待用户确认**：
   - 如果用户补充了新信息 → 更新已掌握的字段，**再次确认**，直到用户表示没有更多信息。
   - 只有当用户**明确表示没有额外信息**（如"没有了""可以了""开始吧"）后，
     才进入"知识加载 → 搜索 → 报告生成"。

> 这一步的目的：报告质量高度依赖输入完整度，提前一轮确认能让你有机会补全遗漏的信息，
> 显著减少返工。**这是硬性流程，不可跳过。**

## 1.6 学历路由（本科 + / 专科 分流）

信息确认完成后、加载知识库前，**先按 `degree` 分流**。专科 / 高职与本科是**赛道差异、不是程度差异**
（院校体系、岗位性质、简历重心都不同，且专科多一条"专升本 vs 直接就业"的主线），两套逻辑分开走、不混用。

| 学历层次 | 走哪条 track | 报告结构模板 | 院校 / 简历知识库 |
|---|---|---|---|
| **专科 / 高职** | **vocational track** | `templates/report-structure-vocational.md`（8 模块） | `references/vocational-schools.md` + `references/vocational-resume-checklist.md` + `references/vocational-zhuanshengben.md`（专升本沉淀框架） |
| 本科 / 硕士 / 博士 | 本科 + track（现有） | `templates/report-structure.md`（8 模块） | `references/school-tiers.md` + `references/resume-checklist.md` |

> **硕士 / 博士走同一套 8 模块结构，但口吻与重点要随学历层次调档**（v1 暂不另设第三条 track）：
> 硕士重"研究方向 / 论文 / 专业纵深"、弱化"GPA/四六级/学生干部"；博士主线是"业界 vs 学界 + 博士专属渠道"，
> 看学术产出而非应届校招那套。**具体调法见 `report-structure.md` 顶部「按 degree 调口吻与重点」**。

- **共用（两条 track 都加载）**：`references/report-style-guide.md`（语气话术）、
  `references/major-career-map.md`（专业→岗位的运行时搜索方法）、`references/resources-guide.md`
  （最后"资源与下一步"模块的中性资源推荐方法）、`references/employer-type-strategy.md`
  （四类雇主的求职策略，按 `target_employer_type` 织入简历/市场/行动/资源模块）、
  `references/resume-rewrite-craft.md`（简历改写范式 + before→after 示范方法，供简历诊断模块用）、
  检索执行机制（三层）、信息确认关卡、输出格式（docx）。
- **两条 track 现已对称（都是 8 模块）**：核心都是**第 3 个"研判"模块**——
  - **本科 track 模块 3 = 求职路径与策略研判**：认清身份/阶段（应届/实习/gap/转专业/考公考研并行）、
    研判方向与投递赛道、给"主攻 + 保底"两手准备。细节见 `report-structure.md`。
  - **专科 track 模块 3 = 升学 vs 就业 路径研判**：立场为**建议"升学 + 就业并行、用就业给升学打保底"**，
    结合**当前年级 + 咨询时间 + 本省专升本考试时间（搜索 5）**判断升学可行性。细节见 `report-structure-vocational.md`。
- **边界 case**（在确认关卡向用户核实，别猜）：
  - 校名含"职业技术大学"等但发**本科**文凭 = **职业本科，属本科 track**，不是专科。
  - "专升本在读 / 专科 + 自考本科" = 已在或已完成升学，按其**当前实际就读层次**判断走哪条 track，
    并在画像里如实说明背景。
  - ⚠️ **简历有多段教育经历时（如专科 + 本科），`degree` 取"当前/最高在读或已获"层次**——
    专升本成功的学生 `degree=本科`、走本科 track，**专科段作为加分背景写进模块 2**（体现学习能力、第一学历提升）；
    若专升本是全日制统招还是自考/成考无法确定（影响第一学历表述），在确认关卡向用户核实。

> 下文"§2 知识加载""§3 搜索""§4 报告生成"中提到的 `school-tiers.md`、`resume-checklist.md`、
> `report-structure.md` 均为**本科 + track** 的默认文件；走专科 track 时，按上表替换为 vocational 对应文件
> 与 8 模块结构，其余流程（搜索机制、确认关卡、docx 输出）完全一致。

## 2. 知识加载

> 下面列的是**本科 + track 默认文件**。走专科 / 高职 track 时，按 §1.6 学历路由把 `school-tiers.md`、
> `resume-checklist.md` 替换为 `vocational-schools.md`、`vocational-resume-checklist.md`；其余共用。

读取以下文件，作为报告对应模块的素材：

- `references/school-tiers.md` → 查找用户学校所在的梯队（模块 2）
- `references/major-career-map.md` → **不是数据表**，而是「专业→岗位方向」的搜索方法与
  输出结构指引。专业种类繁多，**具体的专业对口方向、技能要求、薪资在运行时通过搜索获取
  （见搜索 0），本文件只规定怎么搜、产出哪些维度、格式长什么样**（用于竞争力定位、路径/方向研判、市场、行动等模块）
- `references/resume-checklist.md` → 用于简历诊断（模块 5）
- `references/report-style-guide.md` → 控制报告语气和话术（贯穿全报告）
- `references/resources-guide.md` → 最后一个模块（本科 / 专科均为**模块 8**）「资源与下一步」的方法：
  怎么中性地推荐外部证书 / 课程 / 社区 / 工具 / 求职渠道，怎么标时效与甄别，**不卖任何东西、不导流**。**两条 track 共用**
- `references/employer-type-strategy.md` → 四类雇主（国央企/体制内、互联网大厂&成长民企、外企、中小私企）的
  看重点、简历侧重、笔面试形式、节奏渠道。**按 `target_employer_type` 织入**竞争力定位（模块 2）、路径研判（模块 3）、
  市场分析（模块 4）、简历诊断（模块 5）、行动建议（模块 7）、资源（模块 8）；未指定时对比 2-3 类。**两条 track 共用**
- `references/resume-rewrite-craft.md` → 简历改写范式（STAR 落地模板、专业动词、加粗规则、技能/优势写法）
  + **before→after 改写示范方法**。供简历诊断（模块 5）给出"具体怎么改"与一条改写示范。
  ⚠️ 核心红线：**只基于已有信息扩写、缺数字留占位、绝不替用户编造**。**两条 track 共用**

如果学校不在分档表中，使用通用描述，**不要编造分档信息**。
专业方向不在静态示例中属正常情况——按 `major-career-map.md` 的方法**运行时搜索**即可。

## 3. 实时搜索策略

生成报告前执行以下搜索。下方"搜索 0~4"定义的是**查什么**（查询词与用途）；
具体**怎么查**，统一遵循「检索执行机制（三层）」——优先内置搜索，质量不行就回退抓官方页面，
仍拿不到再走降级。三者配合，确保在不同运行环境下都能尽量拿到真实数据、绝不编造。

> **先分清"沉淀"还是"实时查"，别什么都现查**：
> - **稳定的公开 / 官方 / 权威事实**（如专升本的报考资格、时间规律、与自考成考的区别）查证一次后
>   **沉淀进 `references/` 知识库直接复用**（如 `vocational-zhuanshengben.md`），运行时不重复查。
> - **逐城市 / 逐专业 / 逐年变化的动态信息**（具体城市薪资政策、某专业对口方向、本省当年专升本精确节点）
>   **才走下面的搜索**。沉淀的不重复查、会变的不当成不变——既省力又不把过时信息写成"事实"。

### 搜索 0（前置）：专业对口岗位方向
- 触发条件：用户**未明确 target_direction**，或其专业不在 `major-career-map.md` 的格式示例中
- 查询：`{major} 应届生 对口岗位方向 就业方向 核心技能要求`
- 用途：动态获取该专业可选的 2-3 个主流岗位方向及其技能要求（替代硬编码的专业映射表）
- 处理：按 `major-career-map.md` 规定的输出维度（核心技能/进阶技能/市场需求/薪资/适合人群）
  整理搜索结果；**先于搜索 1 执行**，因为搜索 1 的"方向"参数依赖本步结果
- 填充模块：模块 2（专业匹配度）、模块 3（方向推荐）、模块 6（技能补强）、模块 7（资源）

### 搜索 1：市场与薪资
- 查询：`{target_city} {target_direction 或 major} 就业 薪资 招聘 2026`
- 用途：获取目标城市该方向的薪资区间、岗位供需情况、行业趋势
- 填充模块：模块 3（目标市场分析）

### 搜索 2：政策信息
- 查询：`{target_city} 应届生 就业补贴 落户政策 2026`
- 用途：获取最新的应届生补贴金额、落户条件、人才政策
- **生源地处理**：补贴 / 落户 / 人才引进常区分本地与外地生源。
  - 已知 `hometown` 且与 `target_city` 不同 → 补一条查询 `{target_city} 非本地生源 应届生 落户 人才引进 补贴 2026`，
    分别整理"本地 / 外地生源各自适用什么"
  - 未知 `hometown` → **不替学生判定能否申领**，只罗列政策并标注"是否适用取决于户籍 / 生源地，请自行核验"
- 填充模块：模块 5（政策福利）

### 搜索 3：产业动态
- 查询：`{target_city} {行业关键词} 产业 招聘趋势 2026`
- 用途：获取目标城市产业发展方向、哪些企业在扩招
- 填充模块：模块 3（目标市场分析）

### 搜索 4（可选）：学校就业数据
- 查询：`{school} 就业质量报告 毕业生去向`
- 用途：如果能搜到该校的就业质量报告，作为分析素材
- 填充模块：模块 2（竞争力评估）

### 搜索 5（仅专科 / 高职 track）：专升本**动态信息**
- 触发条件：**走 vocational track 时执行**（本科 + track 不需要）
- ⚠️ **先看知识库，再决定查什么**：专升本的通用框架（仅应届可考 / 一次机会 / 报名早于考试的时间规律 /
  与自考成考区别）**已沉淀在 `references/vocational-zhuanshengben.md`，是稳定权威事实、直接用、不要再查**。
  搜索 5 **只查逐省逐年逐专业变化的动态信息**：
  - 查询：`{省份} 统招专升本 {当前/次年年份} 报名时间 考试时间`（取**本省当年精确节点**）、
    `{省份} 专升本 {当前年份} 政策 改革`（看当年有无扩招/资格调整）、必要时
    `{省份} {专业} 专升本 对口本科院校 报录比`（对口院校与竞争度）
- 用途：拿到本省**当年**的精确节点与竞争情况，配合知识库框架，供模块 3 判断"还来不来得及"、模块 7 排时间线
- 处理：**以搜到的本省官方最新公告（省教育考试院 / 教育厅）为准**；结合学生**当前年级 + 当前咨询日期**判断；
  **搜不到精确时间就提示"以本省教育考试院最新公告为准"并按年级给方向性判断，绝不编造日期**
- 填充模块：模块 3（升学 vs 就业 研判）、模块 7（行动时间线）

### 检索执行机制（三层）

上面每条搜索都按下面的顺序执行，前一层够用就停，不够再降到下一层：

**第 1 层 — 内置 WebSearch（首选）**
- 直接用 WebSearch 跑搜索 0~4 的查询词。
- ⚠️ 已知局限：WebSearch 可能是非中国大陆节点，查"城市政策 / 本地薪资"等中文本地信息时，
  结果常混入大量无关项（英文招聘、海外网站、广告），或只返回过时旧闻。
- **质量自检**：拿到结果后判断——是否命中目标城市/方向的中文本地信息？数字是否够新（贴近当前年份）？
  命中且新 → 采用，进入数据来源标注；**噪音多、过时或答非所问 → 进第 2 层**。

**第 2 层 — 抓取官方/本地站点（回退，针对中文本地数据）**
- 适用：政策（搜索 2）、本地薪资与产业（搜索 1/3）这类**强本地、强时效**的中文数据，第 1 层质量不行时。
- 方式：用 `curl` 经 Jina Reader 抓取页面正文（URL 中的中文需 percent-encode）：
  ```bash
  curl -s --max-time 30 "https://r.jina.ai/<目标页面URL>"
  ```
- **数据源优先级（按实测有效性排序，2026-06 真实测试验证）**：
  1. **垂直站直抓**——最有效。按数据类型选站：
     - 薪资 / 岗位供需 → 招聘聚合站（如**职友集 `jobui.com/salary/<城市>-<岗位>/`**），通常有结构化数字；
     - 政策 / 补贴 / 落户 → **当地人社局 / 政府官网（gov.cn）**、当地"本地宝"政务聚合站。
  2. **百度搜索结果页**——`https://r.jina.ai/https://www.baidu.com/s?wd=<编码查询>`。
     对中文政策类收录好、聚合摘要里常直接含关键数字，可据此再抓具体文章页核实。
  3. **Bing 搜索结果页**——`.../bing.com/search?q=...`。⚠️ 实测对中文本地查询噪音极重
     （常返回旅游、百科、海外结果），**仅在百度与垂直站都拿不到时才用，且需大力清洗**。
- 抓取后清洗：用 `grep` 滤掉导航/广告噪音（如 `民办|小学|健康证|绘本|旅游` 等无关词），保留含目标关键词的行。
- ⚠️ **清洗 ≠ 用窄关键词去"抽答案"**：grep 只用来**去噪**，判断有没有数据要**读正文**。
  实测教训：对"汉语言文学就业方向"用窄词 grep+计数，曾误判成"几乎没数据"，而实际百度正文里
  方向（教育/党政/媒体/企业）写得很全。**先把正文读出来再判断，别让窄 grep 把好数据滤没了。**
- 只采信能定位到**明确出处和时间**的内容；抓到的页面同样要做质量自检，不达标 → 进第 3 层。
- 说明：本层零额外依赖（只用 curl + 公网），可在分发后的环境运行。
  （本地若另装了 agent-reach 等更强检索工具，可作为开发期查证增强，但**不写入本 skill 的运行依赖**。）

**第 3 层 — 降级兜底（前两层都拿不到时）**
- 搜索无结果 / 结果不相关 → 该数据点**跳过，不编造**。
- 政策、薪资搜不到具体数字 → 用通用表述兜底（如"建议关注当地人社局官网获取最新政策"），
  并提示用户自行核验、给出官方查询渠道。
- 宁可少给一个数字，也不给一个编的数字。

### 数据来源标注（贯穿三层）
- 第 1/2 层搜索所得 → 标"**据公开信息**"，政策类加注"具体以官方最新公告为准"。
- 知识库中属经验沉淀的 → 标"**基于行业经验**"。
- `school-tiers.md` 中带排名/就业出处的判断（如偏弱 985）→ 标注其具体来源（如"**据软科/校友会排名**"）。
- **能给链接就给可点链接**：薪资/政策等数据，若搜索时拿到了来源页 URL，用 Markdown 链接写出处
  （如 `[职友集](https://www.jobui.com/salary/hangzhou-java/)`、人社局官网），方便用户自查、也更可信。
  **只写真实取得过的 URL，绝不编造链接**；没把握的就只写来源名 + 官方查询渠道名，不硬凑地址。

## 5. 输出格式

**最终交付物必须是 Word(.docx)，不是 Markdown。** 用户拿到的是可直接阅读 / 转发的 Word 文档。

生成流程（两步）：

1. **先写 Markdown 中间稿**——按模块把报告内容写成一个 `.md` 文件（便于你组织结构、也方便留档）。
   文件名：`{school}_{major}_{target_city}_求职分析与发展规划报告.md`
2. **再转 .docx**——调用本 skill 自带的转换脚本：

   ```bash
   python3 scripts/build_docx.py "<报告.md>" "<同名.docx>"
   ```

   脚本会输出 `{school}_{major}_{target_city}_求职分析与发展规划报告.docx`，**干净中性排版**
   （无品牌 logo，页脚居中页码"第 X 页"）。转换完成后，把 **.docx** 交付给用户（.md 作为留档/可选）。

**为什么用这个脚本，不用 pandoc / textutil / python-docx：**
- 转换**只依赖 python3 标准库**（.docx 本质是装着 XML 的 zip，脚本用 `zipfile` 直接生成）。
  不需要联网安装、不依赖系统里"碰巧装了"的工具——**任何装了本 skill 的使用者都能转**，这是硬要求。

**报告 Markdown 的写法约束**（保证转换效果）：
- 标题用 `#` / `##` / `###`；正文用空行分段；强调用 `**加粗**` / `*斜体*`。
- 列表用 `- `；需要表格时用标准 Markdown 表格（`| … |` + `| --- |`），脚本会转成 Word 原生表格。
- 不要写 HTML、图片、代码块等模板里没有的元素（脚本不解析，会被忽略）。
- **不要在段首手动敲空格做缩进**——转换脚本会自动给正文段落加"首行缩进 2 字符"（标题/小标题/列表/引用不缩进）。
  手动加空格会和自动缩进叠加，反而错位。

## 5.1 交付前内容自检（出厂关卡，必经）

**转 .docx 之前，先对 Markdown 中间稿逐项过一遍下面的清单**。这是给真实用户的成品，
一处残留就会砸掉整份报告的可信度——**任一项不过关，回去修好再转、再交付，不要带病交付**：

- [ ] **无残留占位 / 半成品**：全文搜一遍，没有 `[补充具体数字]`、`XX`、`TODO`、`待补充`、
      `{school}` 之类未替换的模板占位（**用户该填的占位除外**——那种要么明确标成"建议你补充：…"，要么删掉，
      不能裸露在正文里像是漏写）。
- [ ] **姓名 / 院校 / 专业一致**：报告里的姓名、学校、专业、毕业年份前后一致，且与简历一致；
      若简历自身就有不一致（如正文名与文件名不符），应在简历诊断里如实指出，而不是在报告里随机选一个。
- [ ] **每个数字都有出处或明确兜底**：薪资、政策、报录比等数字，要么来自搜索且可溯源，
      要么标注"以官方 / 平台最新信息为准 / 未能查到确切数据"——**没有任何一个数字是凭印象硬写的**。
- [ ] **市场数据链接有效**：引用的招聘平台 / 政策页链接确实是搜索中拿到的真实 URL，不是编的。
- [ ] **无 PII 泄漏**：正文没有回显手机号 / 身份证号 / 家庭住址 / 生日等敏感信息（称呼只用姓名，地域只到城市/省份）。
- [ ] **全文长度达标**：整篇约 **2800-4000 字**（速览半页 + 8 模块各落在篇幅上限内）。**明显超过 ~4500 字就回去压缩**——
      逐模块对篇幅上限，删冗余、并句、去重复，尤其「核心结论速览」压在半页内、「简历诊断」只留 3-5 项。太长读者读不动、也废了速览。
- [ ] **开头速览与正文一致**：「核心结论速览」里的每条结论，正文对应模块都能找到依据，没有速览独有的新判断。
- [ ] **无推销 / 导流 / 品牌**：全文无套餐、价格、"联系某某老师 / 我们能帮你"、公司名 / logo 等任何业务成分。
      （**唯一例外**：A 版末尾分隔线下的升级说明，见 §5.2；B 版及所有正文内容仍严格零推销。此自检针对**报告正文**——A 版那行说明在正文之外，不算违规。）
- [ ] **无机器味尾巴**：结尾没有"本报告由 xx 生成 / 仅供参考 / 免责声明"这类脚注（时效说明已在开头「信息说明」交代）。

> 这一关只看**内容**；`scripts/build_docx.py` 跑完后再确认排版（无 logo、有页脚页码、表格正常）。两关都过才交付。

## 5.2 A/B 双版本产出（速览版 + 完整版）

过完 §5.1、转出完整报告后，按下面的规则**再拆一个 A 版**。最终交付两个 .docx。

**B 版（完整版）= §5.1 过关后的那份报告，一字不动。**
- B 版**严格遵守 §5.1 的"无推销/导流/品牌"**——**绝不**加任何升级说明、价格、联系方式。它的纯净是可信度的来源，是底线。

**A 版（速览版）= 从 B 版里截取 + 一行升级说明。**
1. **内容**：只保留 ①报告标题 ②「核心结论速览」整段（一句话定位 + 3 条关键发现 + 本周 3 件事 + 主攻/保底方向 + 信息说明）③「简历诊断」里的**速查评级表**（那张 ❌/⚠️/✅ 的维度表，不含后面的深挖与改写示范）。其余 8 大模块的展开内容**全部不放进 A 版**。
2. **升级说明（A 版唯一允许的商业行，且必须放在正文之外）**：在 A 版**最末尾**，用一条 `---` 分隔线隔开，加一段**信息型、不油腻**的说明。模板：

   ```
   ---

   *以上是你的求职速览诊断。完整版报告在此基础上展开为 8 个部分——竞争力定位、求职路径研判、目标市场行情、简历逐条诊断与 3–5 处改写示范、政策福利、按「本周/本月/1–3 个月」拆好的行动清单、可自取的资源指引，全文约 3000 字。如需完整版，可补差价升级。*
   ```

   - 这段是**唯一**的例外，只能出现在 **A 版末尾、分隔线之下**，措辞限信息型（讲清完整版多了什么），**不写具体价格数字、不写"联系我/加微信"**（价格在闲鱼商品页谈，报告里不放）。
3. **文件名**：A 版用 `{school}_{major}_{target_city}_求职速览诊断.docx`（与 B 版的"求职分析与发展规划报告"区分）。

> **为什么这么设计**：B 版保持零推销 = 守住可信度底牌；A 版的升级说明放在正文之外的分隔线下、且只讲信息不报价 = 既给了低价入口的转化钩子，又不让分析内容沾上推销味。**顺序不能反**——必须先有过关的 B 版，再从它截 A 版，保证 A 版每一句都是 B 版里验证过的内容。
