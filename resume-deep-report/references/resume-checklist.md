# 简历诊断 Checklist（本科 + track）

## 使用说明
本文件是简历诊断的**维度池**。报告**模块 5（简历诊断）**的写法分两步：

1. **先出「简历健康度速览」**：对下面 7 个维度各给一个评级——**✅ 强 / ⚠️ 中 / ❌ 弱**，
   用一张小表呈现（维度 | 评级 | 一句话结论），**表格后补一句总评定调**。评级基于该维度下命中的检查项数量与严重度。
2. **再深挖标红/标黄的 3-5 项**：只对评为 ❌/⚠️ 的维度展开，每条给
   **问题是什么 → 为什么影响求职 → 具体怎么改**，必须指向简历**具体内容**，不泛泛而谈。

> 不要把所有检查项都倒进报告——速览给全貌，深挖只挑这位用户真正的短板（通常 3-5 条）。

> **重心自适应（重要）**：先看速览的总体分布，再决定诊断模块的着力点——
> - **强简历（≥5 个 ✅）**：别硬凑弱项。转为"优势如何讲到顶 + 1-2 个从优秀到顶尖的提升点"，把篇幅让给路径与投递策略（强简历瓶颈往往不在简历本身）。
> - **空 / 弱简历（大半 ❌）**：别逐条列"这也没有那也没有"。点到关键缺口后，重心转向"先去积累"（补实习/项目/考证），抓手让给行动建议模块。
> - **中等简历**：诊断模块的**主场**，正常深挖。
> ⚠️ 内容太少的简历，"真实性一致性"维度可能因"无内容可夸大"而显 ✅——别让单维误导成"简历没问题"，靠**总评定调**。

> **雇主类型适配**：若已知 `target_employer_type`，诊断的侧重要随之调整（见 `employer-type-strategy.md`）——
> 例如冲**国央企**要额外检查"学历/四六级/党员/学生干部/获奖是否突出、排版是否规整"；冲**互联网大厂**要额外检查
> "项目深度、算法/工程能力、GitHub"；冲**外企**要检查"有无英文版、STAR、leadership 体现"。

> **改法与示范**：每条"具体怎么改"的范式（STAR 落地结构、专业动词、加粗亮点）以及 before→after 改写示范，
> 统一见 `resume-rewrite-craft.md`。核心红线：**只扩写不编造、缺数字留占位**。

## 维度 1：求职定位与 JD 对齐
- [ ] **求职方向与简历主体不一致**（如简历写"嵌入式/C# 方向"，但目标是 Java 后端）
      影响：HR 困惑"你到底想做什么"，匹配度被判低
      建议：按目标岗重写主线，相关经历前置、加重；不相关的压缩为"附加能力"
- [ ] **没针对目标岗位定制**，一份简历投所有方向
      影响：泛而不精，命中率低
      建议：每个方向一版，突出相关经验与关键词
- [ ] **缺目标岗 JD 的关键技能/经验（must-have 未命中）**
      影响：可能被 ATS 简历系统直接过滤，HR 也判定不对口
      建议：对照目标岗 JD 的硬性要求，逐条核对简历是否覆盖、缺的补上或用可迁移经历补位
- [ ] 简历无"求职意向"栏或意向模糊
      影响：HR 需要自己猜你想投什么
      建议：开头明确写"求职意向：XX 岗位（城市）"

## 维度 2：教育背景呈现
- [ ] GPA 未写明或偏低（<3.0/4.0 或 <75/100）
      影响：部分企业有 GPA 筛选线（尤其国企/外企）
      建议：GPA 不突出 → 写专业排名百分比（如前 30%）；确实偏低 → 不写数字，用项目/竞赛弥补
- [ ] 未标注学校层次（211/985/双一流）
      影响：HR 快速筛选时可能误判
      建议：学校名后括号标注（如：河北工业大学（211））
- [ ] 主修课程/学位信息缺失或与目标岗无关堆砌
      影响：版面浪费或显得不对口
      建议：只保留与目标岗相关的核心课程，3-6 门即可

## 维度 3：技能深度与分级
- [ ] 技能描述过于笼统（如只写"熟悉 Java"），无分级
      影响：无法判断掌握深度
      建议：用"精通/掌握/熟悉/了解"分级 + 具体框架版本，核心技能补一句证据
- [ ] 技能列表过长（>15 项），没有重点
      影响：显得什么都会但什么都不精
      建议：按目标岗精选 8-10 项核心技能，分主次排列
- [ ] 技能与项目脱节（列了某技能，但没有任何项目/经历佐证）
      影响：被认为"是不是只是听过"
      建议：删掉无佐证的技能，或补一段用到它的经历

## 维度 4：项目与实践质量
- [ ] 项目只写"做了什么"，没写"结果/成果"（无量化）
      影响：无法体现个人贡献和能力
      建议：STAR 法则重写——不要写"负责用户模块开发"，要写"独立设计实现用户模块（注册/登录/权限），
            支撑 5000+ DAU，接口响应 <50ms"
- [ ] 项目全部是课程作业，没有实战项目
      影响：竞争力弱于有实习/开源项目的同学
      建议：把一个课程项目扩展为完整项目并部署上线；或参与开源；或做解决真实问题的 side project
- [ ] 团队项目没体现个人角色
      影响：面试官无法判断你具体做了什么
      建议：明确标注"个人负责：xxx"，量化个人贡献
- [ ] **（技术/设计/数据岗）缺 GitHub / 作品集 / 个人主页链接**
      影响：技术岗这是直接加分的硬佐证，缺了等于少一张牌
      建议：放上 GitHub / 作品集链接，确保里面有像样的内容（别放空仓库）

## 维度 5：实习经历厚度
- [ ] 没有任何实习经历
      影响：无实习是明显短板（尤其临近或已过毕业季时）
      建议：优先找 1-3 个月短期实习快速补上；暂时找不到则用高质量项目 + 竞赛弥补
- [ ] 实习描述过于简单（一两句话带过）
      影响：浪费了最有说服力的经历
      建议：每段实习写 3-5 条具体工作内容和成果（带数字）
- [ ] 实习与目标岗不对口
      影响：方向散，竞争力弱
      建议：提炼可迁移的能力往目标方向讲；后续力争一段对口实习

## 维度 6：真实性与一致性（HR 的"扣分雷达"，最容易被忽视）
- [ ] **时间线有重叠 / 倒置**（如某段经历"结束早于开始"，或两段全职时间冲突）
      影响：硬伤，被视为不严谨甚至造假，直接出局
      建议：逐段核对起止时间，确保不冲突、不倒置
- [ ] **夸大词泛滥**（满屏"精通""资深""专家级"，但无对应深度）
      影响：HR 一眼看穿，反噬可信度
      建议：把"精通"降级为名副其实的"掌握/熟悉"，用证据而非形容词说话
- [ ] 经历/成果无法被佐证（数字夸张、头衔与内容不符）
      影响：面试一问就露馅
      建议：只写经得起追问的内容，数字要能解释来源

## 维度 7：可读性与专业感
- [ ] 简历超过一页（应届生）
      影响：应届简历超一页会被视为不专业
      建议：精简到一页，删与目标岗无关内容
- [ ] 条目不以动词开头 / 大段第一人称叙述
      影响：读起来啰嗦、不专业
      建议：每条用动词开头（"主导/设计/实现/优化…"），去掉"我负责了…我还…"
- [ ] 中英文混杂不当、错别字、格式/字体混乱
      影响：细节暴露态度
      建议：有对应中文就用中文；通读校对错别字；统一字体、字号、对齐与项目符号
- [ ] 排版拥挤或留白失衡、缺分区标题
      影响：HR 几秒扫不到重点
      建议：清晰分区（教育/技能/项目/实习），重点信息加粗、靠前

---

> 维度池可继续扩充，但**报告永远只呈现"速览 + 深挖命中项"**，不堆砌全部条目。
