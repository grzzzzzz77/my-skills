# C 端小程序体验评审

在开发投入前，把“感觉不好用”转成有证据、可排序、可落地、可验收的问题。评审对象可以是单页、弹窗、完整任务链路或多步漏斗。

## 先判断证据模式

使用当前可得的最强证据，不得把较弱证据伪装成实际体验结论：

- `spec_only`：只有 PRD、流程说明或文字规则。可以审查逻辑、路径和状态完整性；不能确认真实视觉、点击反馈、性能或可访问性实现。
- `static_artifact`：有线框图、原型图、截图、Figma/Axure 导出物。可以审查布局、层级、文案和可见状态；不能确认真实跳转、手势、动效、焦点和耗时。
- `interactive_flow`：有可操作原型、测试版小程序或 H5。可以观察实际行为；只有在用户授权且环境可访问时操作。真实支付、真实提交、生产数据修改和对外触达仍需单独授权。

每条结论标记证据等级：

- `observed`：本轮实际看到或操作验证。
- `specified`：PRD、标注或用户明确说明。
- `inferred`：基于现有材料推断的风险，必须说明假设。
- `unknown`：材料不足，不能判断。

## 必读参考

- 每次评审都完整读取 [references/review-framework.md](references/review-framework.md)。
- 需要完整报告、评分、PRD 回写或验收标准时，再读取 [references/report-contract.md](references/report-contract.md)。
- 用户要求机器可校验 JSON、严格模式或 95+ 质量门禁时，再读取 [references/strict-json.md](references/strict-json.md)，并运行 `scripts/validate_review.py`。

## 评审流程

### 1. 固定体验契约

先写清：目标用户、使用情境、核心任务、成功结果、业务约束、评审范围和明确非目标。缺失信息可采用可逆假设，但必须标为 `inferred`；只有会实质改变用户、任务或流程时才追问。

### 2. 建立证据清单

列出本轮实际读取或操作的 PRD、页面、原型帧、截图、链接、录屏和说明。没有读到的材料不得作为证据。先写证据限制，再开始判断。

### 3. 按用户任务走完整流程

从真实入口开始，逐步记录：用户意图、可见信息、动作、系统反馈、下一步、退出/返回和恢复方式。不要只审查单张主界面；覆盖首次使用、重复使用、中断后返回和关键分支。

### 4. 检查状态与异常闭环

为适用场景检查初始、加载、空、部分成功、成功、失败、无权限、离线、超时、登录失效、重复提交和版本不兼容。状态不适用时写明理由，不得为了凑表虚构状态。

### 5. 分层审查

先处理结构性问题，再处理视觉细节：

1. 用户目标、入口与价值是否清楚。
2. 信息架构、主次层级和决策负担。
3. 操作步骤、重复输入和不可逆动作。
4. 系统状态、即时反馈和进度可见性。
5. 错误预防、失败恢复和中断续接。
6. 登录、授权、隐私、支付与信任感。
7. 小程序导航、胶囊区、安全区、键盘、滚动和返回习惯。
8. 触控面积、对比度、文字缩放、读屏语义和动效降级风险。
9. 文案、按钮语义、视觉一致性与品牌表达。

### 6. 生成唯一问题台账

每个问题只保留一个 `finding_id`，避免同一根因在多个维度重复扣分。每条包含：所在步骤、问题、用户影响、证据、严重度、置信度、建议和验证方法。

严重度规则：

- `P0`：核心任务不可完成，或存在严重的资金、隐私、数据丢失、误操作与信任风险。
- `P1`：显著降低完成率、造成高频困惑/返工，或形成重要无障碍障碍。
- `P2`：不阻断任务，但影响效率、一致性、可读性或专业感。
- `Opportunity`：可探索的增强项，不伪装成已证实问题。

### 7. 输出可落地改法

建议必须说明改什么、为什么、影响哪个步骤、依赖什么、如何验证。优先给最小可行修正；只有结构确实失效时才提出重构流程。不得凭空发明业务规则、指标阈值或平台能力。

### 8. 回写 PRD

把确认后的改动转成业务规则、状态机、异常路径、文案规则、埋点建议和 Given/When/Then 验收标准。把事实、建议、假设和待确认项分开。

## 交付规则

默认在聊天中输出简洁完整报告；用户指定文件时再保存。报告至少包含：

1. 总体结论、范围和证据等级。
2. 用户目标与任务链路。
3. P0/P1/P2 问题台账。
4. 状态与异常矩阵。
5. 优化后的流程/UI/交互方案。
6. PRD 回写项与验收标准。
7. 证据限制和后续验证计划。

产品体验分只在用户要求评分或需要比较版本时输出，并同时给出证据置信度。不得用一个高分掩盖 P0/P1，也不得把静态图评分说成真实可用性测试。

## 95+ 质量门禁

在交付前按 [references/report-contract.md](references/report-contract.md) 的“报告质量分”内部自检，最多进行三轮修订：

- `>=95` 且所有硬门禁通过：可以交付。
- `<95`：修正证据、流程、状态、问题结构或验收缺口后重新评分。
- 三轮后仍不足：标记为 `Incomplete`，说明缺少的证据；不得虚增分数。

机器可校验模式必须运行：

```bash
python3 scripts/validate_review.py <review.json> --min-score 95
```

验证脚本的 95 分表示报告结构与证据闭环质量，不表示产品体验达到 95 分。
