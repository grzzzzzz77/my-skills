# C 端小程序体验评审框架

本框架用于做产品体验判断，不是视觉风格清单。先判断用户能否理解并完成任务，再判断页面是否精致。

## 1. 体验契约

开始前建立最小契约：

| 字段 | 要求 |
|---|---|
| 目标用户 | 角色、熟练度、设备/环境、时间压力 |
| 核心任务 | 用户此刻真正想完成的事，而不是页面功能名 |
| 成功结果 | 用户可感知、可验证的完成状态 |
| 业务目标 | 转化、留存、效率或风险控制；没有证据时不编指标 |
| 评审范围 | 起点、终点、包含页面和关键分支 |
| 非目标 | 本轮明确不判断的内容 |

## 2. 任务链路审查

每一步至少回答：

- 用户为什么会来到这里，入口是否可发现。
- 页面是否解释“这是什么、能做什么、下一步是什么”。
- 主操作是否唯一清晰，次要操作是否抢占注意力。
- 用户需要记忆、比较、填写或确认多少信息。
- 系统是否在点击后及时反馈，等待是否可理解。
- 返回、取消、中断和重新进入后是否保留上下文。
- 失败时用户能否知道原因、保留已输入内容并恢复。
- 完成后是否明确告知结果、下一步和可撤销性。

首次用户与熟练用户分别检查。首次用户需要解释与安全感，熟练用户需要减少重复和等待；不能只优化其中一类。

## 3. 核心审查维度

需要评分时使用以下 100 分体验维度；不需要评分时仍按这些维度检查。每项先给证据，再给分数。

| 维度 | 权重 | 核心问题 |
|---|---:|---|
| 目标与入口 | 10 | 用户能否快速理解价值并找到入口 |
| 流程与效率 | 15 | 是否存在多余步骤、重复输入或断裂跳转 |
| 信息架构与层级 | 10 | 内容分组、主次和页面定位是否清楚 |
| 认知与决策负担 | 10 | 是否让用户记忆、猜测或一次处理过多选择 |
| 反馈与状态可见性 | 10 | 点击、等待、进度和结果是否及时明确 |
| 异常与恢复 | 15 | 失败、中断、无权限和重复提交能否恢复 |
| 信任、隐私与授权 | 10 | 是否说明目的、影响、撤销方式和敏感操作 |
| 触控与可访问性 | 10 | 触达、对比、缩放、读屏、动效是否存在风险 |
| 平台与视觉一致性 | 5 | 导航、安全区、组件和视觉语言是否一致 |
| 文案与行动语义 | 5 | 标题、提示、按钮和错误文案是否具体 |

评分不能代替问题台账。存在 P0 时总体结论不得为“健康”；存在未关闭 P1 时不得仅凭平均分宣称“可以直接开发”。静态材料只能得到设计风险分，不能得到真实任务成功率。

## 4. 小程序特有检查

只检查与当前流程相关的项：

### 入口与再进入

- 搜索、扫码、分享卡片、公众号/消息、最近使用等入口是否落到正确上下文。
- 冷启动、热启动、分享深链和登录失效后的返回路径是否一致。
- 中断后重进是否保留表单、筛选、购物车、步骤和来源信息。

### 登录、授权与隐私

- 不要在用户理解价值前无差别要求登录或手机号。
- 相机、相册、定位、通知等权限应在使用情境中解释用途。
- 拒绝授权后提供替代路径、重新授权入口和可理解的恢复说明。
- 收集敏感信息时说明必要性、使用目的与可控范围。

### 导航与容器

- 顶部内容避开状态栏和小程序胶囊区，底部主操作避开系统安全区。
- Tab 只承载稳定的顶层目的地；返回行为与用户预期一致。
- 避免弹层套弹层、横向手势与系统返回冲突、主滚动区嵌套多个滚动区。
- 键盘弹出后输入框、错误信息和提交按钮仍可见、可操作。

### 网络与异步

- 进入页、列表、详情和提交操作有合适的加载、骨架、空与失败状态。
- 防止重复提交；慢网、离线、超时和接口部分成功有明确反馈。
- 列表刷新、分页和缓存不能突然改变滚动位置或覆盖用户输入。

### 敏感与不可逆操作

- 支付、删除、发布、退出、解绑等操作在执行前确认对象和后果。
- 处理中防重复操作；成功后给凭证，失败后给原因和恢复路径。
- 可撤销的操作优先提供撤销；不可撤销时明确警示但避免制造恐慌。

### 触控与无障碍

- 关键触控区域建议至少约 44×44 CSS px/pt 等效面积，并保留足够间距；以目标平台最新规范为准。
- 图标按钮有可理解标签，颜色不是唯一状态信号。
- 正文、次要文字和禁用态保持可读对比；文字放大后不遮挡核心操作。
- 动效不应阻塞操作，需考虑减少动态效果；静态稿只能标为风险，不能确认实现合规。

## 5. 状态与异常矩阵

每个状态写：触发条件、系统行为、用户可见反馈、允许动作、恢复方式、埋点/日志建议。至少逐项判断：

- `initial`
- `loading`
- `empty`
- `partial_success`
- `success`
- `failure`
- `no_permission`
- `offline`
- `timeout`
- `session_expired`
- `duplicate_submit`
- `unsupported_version`

状态可以标记 `not_applicable`，但必须说明为什么。不要为了完整而制造产品不需要的状态。

## 6. 发现项写法

一条合格发现项必须形成闭环：

```text
F-03｜P1｜步骤 S2｜specified｜置信度 High
问题：手机号授权在用户看到服务价值前强制出现。
影响：首次用户无法判断授权收益，可能直接退出，且拒绝后没有替代路径。
证据：PRD 2.1 写明进入首页立即弹出手机号授权。
建议：先展示核心内容，在触发预约时说明用途并请求授权；拒绝后允许浏览并提供手动手机号方案。
验证：首次用户无需授权可浏览；点击预约时出现用途说明；拒绝后仍能继续并找到替代入口。
```

同一个根因只创建一个 finding。关联到多个步骤时列出关联步骤，不复制问题和扣分。

## 7. 建议质量

优先级顺序：

1. 修复任务阻断、误操作、资金/隐私/数据风险。
2. 缩短核心路径并补齐状态、反馈和恢复。
3. 降低认知负担，改善信息架构和文案。
4. 统一视觉、触控和动效细节。

建议应适配现有设计系统和平台能力。竞品只能作为比较上下文，不能代替用户证据；没有数据时不声称某改动会提升具体转化率。
